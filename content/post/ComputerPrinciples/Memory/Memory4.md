## 前言

栈解决了函数本地数据的需求，但有两个根本限制：大小在编译期必须确定，生命周期与函数调用绑定。

现实中大量需求都打破这两条：

- 用户输入了多少字符，运行前不知道 → 大小不确定
- 函数 A 创建的数据要传给函数 B 继续用 → 生命周期超出函数范围

这就是**堆（Heap）**存在的原因：一块由程序员（或运行时）手动管理的内存区域，可以在运行时动态分配、任意大小、任意生命周期。

## 堆的基本操作

### malloc 与 free（C 语言视角）

C 语言通过 `malloc` / `free` 直接操作堆：

```c
#include <stdlib.h>
#include <string.h>

int main() {
    // 在堆上分配 10 个 int 的空间（40 字节）
    int *arr = (int*)malloc(10 * sizeof(int));
    if (arr == NULL) {
        // malloc 失败时返回 NULL，必须检查
        return 1;
    }

    // 使用这块内存
    for (int i = 0; i < 10; i++) {
        arr[i] = i * i;
    }

    // 用完必须手动释放，否则内存泄漏
    free(arr);
    arr = NULL; // 良好习惯：避免悬空指针
    return 0;
}
```

`malloc(n)` 返回一个 `void*`，指向刚分配的 `n` 字节内存，调用方负责记住这个指针并在合适的时候调用 `free`。

### 常见的堆操作函数（C）

```c
void* malloc(size_t size);          // 分配 size 字节，不初始化
void* calloc(size_t n, size_t size);// 分配 n*size 字节，初始化为 0
void* realloc(void* ptr, size_t size);// 调整已分配内存的大小
void  free(void* ptr);              // 释放内存
```

`realloc` 是个有趣的操作——如果当前块后面有足够空闲内存，就原地扩展；如果没有，就分配一块更大的内存、复制数据、释放旧块。这就是为什么 `realloc` 可能让指针变化。

## 内存分配器的工作原理

`malloc` 背后是**内存分配器（Memory Allocator）**，它管理着从操作系统申请来的大块内存，按需切分给程序。

### 操作系统级别：brk 和 mmap

分配器向操作系统申请内存有两种方式：

- **`brk` / `sbrk`**：调整堆的上边界（program break），向上移动意味着申请更多堆内存。适合小块、频繁分配。
- **`mmap`**：映射一块匿名内存，可以在地址空间任意位置申请。适合大块分配（通常 >= 128 KiB）。

```
 n 较小（< 128 KiB） → 从分配器自己管理的池子里切一块
n 较大（>= 128 KiB）→ 直接用 mmap 向操作系统申请一块，单独管理
```

### 空闲链表（Free List）

分配器内部用**空闲链表**记录哪些内存块可用。每个空闲块的开头有一个元数据头，记录块大小和空闲标志；块的末尾有脚部（用于从后向前合并）。

堆内存在分配器内部表现为一连串块，每块头部有一个元数据，记录块大小（32 位）和是否已分配（1 位）。块末尾附有脚部，便于从后向前合并相邻的空闲块。

**分配请求**到来时，分配器遍历空闲链表，找一个足够大的空闲块：

- **首次适配（First Fit）**：找第一个足够大的块，速度快但容易在低地址堆积碎片
- **最佳适配（Best Fit）**：找最小的足够大的块，碎片少但遍历慢
- **分离适配（Segregated Fit）**：按大小分类维护多个空闲链表，综合性能最好（glibc 的 ptmalloc、jemalloc、tcmalloc 都采用类似思想）

**释放操作**时，分配器把块标为空闲，并尝试**合并（Coalesce）**相邻的空闲块，防止碎片化：

```
释放中间那块后的合并：

释放前：  [已分配] [空闲 32B] [待释放 64B] [空闲 32B] [已分配]
释放后：  [已分配] [       空闲 128B       ] [已分配]
```

### 内存碎片

即使总空闲内存足够，也可能分配失败——这叫**外部碎片（External Fragmentation）**：

比如，内存里有三个空闲块分别是 30B　80B　90B，共计 200B，但无法满足一个 150B 的连续分配请求。

还有**内部碎片（Internal Fragmentation）**：分配器为了对齐（alignment）会把小请求向上取整到最近的 8 或 16 字节边界，导致实际分配比请求大：

比如请求 17 字节，分配器为了对齐到 8 的倍数会实际分配 24 字节，浪费 7 字节的内部碎片。

## C++ 的 new/delete

C++ 的 `new`/`delete` 是对 `malloc`/`free` 的封装，额外调用构造函数和析构函数：

```cpp
// C++ 分配单个对象
MyClass* obj = new MyClass(args...);  // malloc + 构造函数
delete obj;                            // 析构函数 + free

// 分配数组
int* arr = new int[100];
delete[] arr;  // 注意必须用 delete[]，否则只会调用第一个元素的析构函数
```

`new` 失败时抛出 `std::bad_alloc` 异常（而不是返回 NULL），这是 C++ 和 C 的一个重要区别。

## Rust 的堆管理

Rust 通过**所有权系统**在编译期保证堆内存安全——不需要手动 `free`，也不需要垃圾回收器，而是在所有者的作用域结束时自动释放。

```rust
fn main() {
    // Box<T>：在堆上分配 T，所有权绑定到 box 这个绑定
    let box_val = Box::new(42_i32);
    println!("{box_val}"); // 解引用自动发生

    // box_val 的作用域结束，Box 被 drop，堆内存自动释放
}
```

`Box::new` 在底层调用全局分配器（默认是系统的 `malloc`），`Box` 的 `Drop` 实现负责在析构时调用 `free`。

```rust
fn main() {
    let v: Vec<i32> = vec![1, 2, 3, 4, 5];
    // Vec 内部持有三个字段：指向堆上数组的指针、长度、容量
    // v 离开作用域时，Vec 的 Drop 实现会 free 堆上的数组
    println!("{v:?}");
}
```

Rust 的所有权模型保证了：**堆内存恰好被释放一次，不多也不少**。而 C/C++ 的常见问题——双重释放（double free）、悬空指针、内存泄漏——在 Rust 里要么编译不过，要么由类型系统杜绝。

## 常见的堆内存 Bug

### 内存泄漏（Memory Leak）

分配了内存，但忘记 `free`：

```c
void leak() {
    int *p = malloc(100);
    if (some_error) return; // 提前返回，p 没有被 free
    // ...
    free(p);
}
```

内存泄漏不会立刻崩溃，但程序运行越久，占用内存越多，最终被 OOM Killer 杀掉（Linux）或出现性能下降。

### 悬空指针（Dangling Pointer）

释放内存后继续使用：

```c
int *p = malloc(4);
free(p);
*p = 42; // 未定义行为！内存可能已被重新分配给别的用途
```

### 双重释放（Double Free）

同一块内存释放两次：

```c
int *p = malloc(4);
free(p);
free(p); // 未定义行为，可能破坏分配器的内部数据结构
```

### 缓冲区溢出（Buffer Overflow）

写入超出分配边界的内存：

```c
int *arr = malloc(5 * sizeof(int));
for (int i = 0; i <= 5; i++) { // i <= 5，越界写入 arr[5]
    arr[i] = i;
}
// arr[5] 覆盖了相邻内存块的 header，可能导致分配器崩溃或安全漏洞
```

缓冲区溢出是历史上最严重的安全漏洞来源之一（堆溢出可以覆盖分配器元数据或其他对象，实现任意代码执行）。

## 堆 vs 栈：如何选择

和栈相比，堆的分配和释放都更慢：栈只需移动一个寄存器（一条指令），堆要让分配器遍历空闲链表、更新元数据。但堆的优势是容量几乎不受限制，数据的大小不需要在编译期确定，生命周期也不与任何函数调用绑定——你可以在函数 A 里分配，在函数 B 里使用，在函数 C 里释放。这种灵活性正是堆存在的理由。

实践原则：**优先把数据放在栈上**。栈分配开销极低，不会产生碎片，函数返回自动清理。只有在大小编译期未知、数据需要超出当前函数存活，或对象需要被多处共享时，才用堆。Rust 的 `Vec`、`String`、`Box`、`Rc`、`Arc` 都是堆分配，但通过 RAII 保证不泄漏。

## 垃圾回收（GC）

Java、Python、Go、JavaScript 等语言用**垃圾回收器（Garbage Collector）**自动管理堆内存，程序员不需要手动 `free`。

常见 GC 算法：

- **引用计数（Reference Counting）**：每个对象记录被引用次数，为 0 时释放。Python 用这个，实现简单但无法处理循环引用，Rust 的 `Rc`/`Arc` 也是引用计数（但不是 GC，因为不会自动处理循环）。
- **标记-清除（Mark and Sweep）**：从根对象出发标记所有可达对象，清除未被标记的对象。会产生 Stop The World 停顿。
- **分代收集（Generational GC）**：大多数对象"朝生夕死"，把对象按年龄分代，频繁回收新生代（年轻对象），偶尔回收老年代（长寿对象）。JVM、CPython（除引用计数外的补充 GC）都使用。
- **三色标记（Tri-color Marking）**：Go 使用的并发 GC 算法，标记阶段与程序并发执行，减少停顿。

GC 的代价是：停顿（Stop The World）、额外的内存开销（通常需要 2-3 倍实际对象大小的堆空间才能高效运行），以及不可预测的延迟——这也是实时系统、游戏引擎等对延迟敏感的场景往往回避带 GC 语言的原因。

## 小结

堆是动态内存的家园：

- 运行时申请，大小不需要编译期确定
- 生命周期由程序显式控制（或 RAII/GC 自动管理）
- 分配器通过空闲链表管理内存块，处理碎片合并
- C/C++ 需要手动管理，容易出现泄漏/悬空/双重释放
- Rust 的所有权系统在编译期消除上述问题，无需 GC
