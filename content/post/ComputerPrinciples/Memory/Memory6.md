## 前言

第 1 篇讲过，一次 DRAM 访问需要 150~300 个 CPU 时钟周期。一个 3 GHz 的 CPU 每秒执行 30 亿条指令，但每次读内存就要等 100 多纳秒——如果每条指令都要访问内存，CPU 99% 的时间都在等待，性能会惨不忍睹。

CPU 缓存（Cache）就是为了弥合这道速度鸿沟而存在的。

## 局部性原理

缓存能起作用，根本原因是程序的**局部性（Locality）**：

**时间局部性（Temporal Locality）**：刚访问的数据，短时间内很可能再次访问。比如循环里的计数器变量，每轮循环都要读写，就一直待在缓存里。

**空间局部性（Spatial Locality）**：访问某个地址，相邻地址很快也会被访问。遍历数组时，访问 `arr[0]` 之后接着访问 `arr[1]`、`arr[2]`……正好是连续内存，缓存一次性载入一批。

这两条经验规律让"用小而快的缓存保存最近访问的数据"成为可行且高效的策略。如果程序随机蹦跳访问内存、毫无规律，缓存就帮不上忙了。

## 缓存的层次结构

现代 CPU 通常有三级缓存：

L1/L2 是每个核心私有的，L3 在所有核心间共享。容量越大，延迟越高，成本也越高。

- **寄存器** —— ±0 周期（CPU 内部）
- **L1 I/D-Cache**：32~48 KiB，±4~5 周期（每核私有）
- **L2 Cache**：256 KiB~1 MiB，±12 周期（每核私有）
- **L3 Cache**：4~64 MiB，±30~40 周期（多核共享）
- **主内存（DRAM）**：几十 GiB，±150~300 周期

L1 分为指令缓存（I-Cache）和数据缓存（D-Cache），L2/L3 通常统一。L1/L2 是每个核心私有的，L3 在所有核心间共享。容量越大，延迟越高，成本也越高。

## 缓存行（Cache Line）

缓存的基本操作单位不是字节，而是**缓存行（Cache Line）**。

现代 CPU（x86-64、ARM64）的缓存行大小是 **64 字节**。无论你只访问 1 个字节，CPU 都会把那个字节所在的整个 64 字节块一起载入缓存。

访问 `arr[0]`（int32，4 字节）时，CPU 会把 `arr[0]~arr[15]`（共 64 字节，16 个 int）整个载入一条缓存行。後续访问 `arr[1]~arr[15]` 全部命中，零额外延迟——这就是空间局部性可以被利用的物理机制。

这就是空间局部性能被利用的物理机制。

数据结构的起始地址如果是 64 字节的倍数，就与缓存行对齐，可以避免一个数据结构横跨两条缓存行（那样需要两次缓存读取）：

```c
// 显式对齐到缓存行大小
struct alignas(64) HotData {
    double value;
    // ...
};
```

Rust 中用 `#[repr(align(64))]`：

```rust
#[repr(align(64))]
struct AlignedData {
    value: f64,
}
```

## 缓存的组织结构

### 直接映射缓存（Direct Mapped）

每个内存地址只能放入缓存的一个固定位置，由地址的某些位决定。简单但容易**冲突缺失（Conflict Miss）**——两个频繁访问的地址映射到同一缓存槽，相互驱逐对方。

### 全相联缓存（Fully Associative）

内存块可以放入缓存的任意位置，缺失率最低，但查找需要同时比较所有缓存行（并行比较器），硬件成本极高，只在极小的缓存（如 TLB）中使用。

### 组相联缓存（Set-Associative）

折中方案：缓存分为多个**组（Set）**，每组有 N 个**路（Way）**。内存块只能放入特定的组，但在组内可以放任意路。N 路组相联（N-way Set Associative）是现代 CPU 的标准设计。

```
用 Set Index 确定组号 → 并行比较该组所有 8 条缓存行的 Tag
  命中：Tag 匹配且有效 → 返回数据
  未命中：从下级缓存或内存取数据，替换该组中某一条（通常用 LRU）
```

L1 通常 4 路或 8 路，L3 通常 16 路甚至更高。

## 缺失的三种类型（3C 模型）

**强制缺失（Compulsory Miss）**：第一次访问某数据，缓存里必然没有。不可避免，只能通过预取（Prefetch）来提前载入。

**容量缺失（Capacity Miss）**：工作集（程序短时间内访问的全部数据）超过缓存容量，被迫驱逐后又重新访问。可以通过减小工作集、拆分计算阶段来缓解。

**冲突缺失（Conflict Miss）**：组相联度不够高，多个数据映射到同一 Set，相互驱逐。提高相联度或调整数据布局可以缓解。

## 缓存一致性与 MESI 协议

多核 CPU 每个核心有独立的 L1/L2 缓存。当核心 0 修改了某个数据，核心 1 的缓存里可能还有旧值——这就是**缓存一致性（Cache Coherence）**问题。

现代 CPU 用 **MESI 协议**维护一致性。每条缓存行有四种状态：

```
M (Modified)：本核心修改过，内存是旧的，其他核心没有这行
E (Exclusive)：只有本核心有，与内存一致
S (Shared)  ：多个核心都有这行，与内存一致，只读
I (Invalid)  ：这行无效，需要重新从内存或其他缓存获取
```

核心 0 写一条处于 S 状态的缓存行时，会广播 Invalidate 消息，让所有其他核心把这行置为 I；然后本核心变为 M 状态，独占这行。其他核心下次访问这行时，触发缺失，从核心 0 获取最新数据。

MESI 由 CPU 硬件透明处理，程序员通常感知不到。但它的代价是：**频繁在多核间传递同一缓存行，会产生大量总线流量**——这就是伪共享的根源。

## 伪共享（False Sharing）

如果两个线程各自修改不同的变量，但这两个变量恰好在同一条缓存行里，就会发生**伪共享**：每次修改都要 Invalidate 对方核心的缓存行，即使它们操作的是完全不同的数据。

```c
// 典型的伪共享场景
struct Counter {
    int64_t a;  // 线程 0 修改
    int64_t b;  // 线程 1 修改
    // a 和 b 都在同一条 64 字节的缓存行里！
};
```

修复方法是填充（Padding），让每个线程的数据占满一整条缓存行：

```c
struct Counter {
    int64_t a;
    char _pad_a[56]; // 填充到 64 字节
    int64_t b;
    char _pad_b[56];
};
```

Rust 中并发框架（如 crossbeam）提供了 `CachePadded<T>` 包装器，封装了这个模式。

## 写策略

缓存写入时有两种策略：

**写直达（Write-Through）**：写缓存时同时写内存。简单，一致性好，但每次写操作都有内存延迟。主要用于 L1 I-Cache 等特殊场景。

**写回（Write-Back）**：写操作只更新缓存（标为 Modified），等缓存行被驱逐时才写回内存。性能好，但实现更复杂（需要 Dirty 位）。L1 D-Cache、L2、L3 通常用写回。

## 写出缓存友好的代码

理解了缓存工作原理，就能主动写出性能更好的代码。

### 顺序访问

```c
// 矩阵行主序遍历（缓存友好，步长=4字节）
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        sum += matrix[i][j];

// 矩阵列主序遍历（缓存不友好，步长=N*4字节，每次跨一整行）
for (int j = 0; j < N; j++)
    for (int i = 0; i < N; i++)
        sum += matrix[i][j];
```

N=1024 时，行序遍历比列序遍历快 **10~50 倍**。原因：列序每次访问都跳过一整行，无法利用缓存行里已经载入的数据。

### 数组 vs 链表

链表节点在堆上随机分布，遍历时每个节点几乎都是一次缓存缺失；数组连续存储，一条缓存行可以载入多个元素：

链表节点在堆上随机分布，遍历时每次 `->next` 跳转就可能败中缓存，耗费 150+ 周期。数组元素连续存放，一条缓存行可以载入多个元素，后续访问直接命中。这也是 Rust 的 `Vec` 通常比 `LinkedList` 快很多的原因。

这也是为什么 Rust 的 `Vec` 通常比 `LinkedList` 快，即使链表的插入理论上是 O(1)。

### 热冷数据分离

访问频繁的字段（热数据）和不常用的字段（冷数据）分开存放，避免缓存行被冷数据"污染"：

```rust
// 不好的设计：物理更新和渲染属性混在一起
struct Entity {
    position: [f32; 3],  // 每帧更新
    velocity: [f32; 3],  // 每帧更新
    health: f32,          // 每帧更新
    mesh_id: u32,         // 只有渲染时才用
    texture_id: u32,      // 只有渲染时才用
    // ...大量渲染属性，把热数据挤出缓存行
}

// 更好的设计：分离热/冷数据
struct EntityPhysics { position: [f32; 3], velocity: [f32; 3], health: f32 }
struct EntityRender   { mesh_id: u32, texture_id: u32 }
```

这种思路在游戏引擎和高性能计算中称为**数据导向设计（Data-Oriented Design）**。

## 性能剖析：测量缓存行为

Linux 下用 `perf` 工具统计缓存缺失：

```bash
perf stat -e cache-references,cache-misses,L1-dcache-load-misses,LLC-load-misses ./my_program
```

Rust 中可以用 `criterion` 做基准测试，配合 `perf` 或 `cachegrind`（Valgrind）分析缓存行为。

## 小结

CPU 缓存是现代计算机性能的关键所在：

- 缓存行（64 字节）是基本操作单位，读写都以缓存行为单位传输
- L1/L2 是核心私有，L3 是多核共享；三级缓存延迟从 4 周期到 40 周期
- MESI 协议保证多核缓存一致性，伪共享是多线程性能杀手
- 写回策略（Write-Back）让写操作快，代价是需要 Dirty 位管理
- 缓存友好的代码：顺序访问、数组优于链表、热冷数据分离
