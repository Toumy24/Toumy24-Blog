## 前言

每次调用函数，局部变量从哪里来？函数结束后又去哪里？返回值怎么传回给调用方？`main` 调 `foo`，`foo` 再调 `bar`，这条链是怎么维护的？

答案都在**栈（Stack）**里。栈是程序运行时最核心的内存区域之一，理解它，等于理解了函数调用的全部细节。

## 栈的数据结构

"栈"这个名字来自数据结构里的栈——一种后进先出（LIFO, Last In First Out）的容器。想象一摞盘子：只能在顶部放盘子（push），也只能从顶部取盘子（pop）。

内存里的调用栈（Call Stack）遵循同样的规则，但操作的不是盘子，而是**栈帧（Stack Frame）**——每次函数调用对应一个栈帧。

x86-64 上栈向低地址方向生长。main 最先压入，在高地址一侧；foo 在 main 上方，bar 在最顶部（最低地址）。“压栈”意味着 rsp 减小，“弹栈”意味着 rsp 增大。

注意：在大多数架构（包括 x86-64、ARM64）上，栈是**向低地址方向生长**的。"压栈"意味着栈顶指针（rsp）减小，"弹栈"意味着 rsp 增大。

## 栈帧的结构

每个栈帧包含这个函数调用所需的全部信息：

一个典型的 x86-64 栈帧内容（从高地址到低地址）：

1. 调用方传入的参数（若超出寄存器上限）
2. 返回地址（Return Address）——由 `call` 指令自动压入
3. 保存的 `rbp`（旧帧指针）——`rbp` 指向此处
4. 局部变量（可能有多个）
5. 被调用方保存的寄存器——`rsp` 指向此处

### 关键寄存器

- **rsp（Stack Pointer）**：始终指向当前栈顶（最新压入的位置）
- **rbp（Base Pointer / Frame Pointer）**：指向当前栈帧的底部，用于定位局部变量和参数的固定偏移量

通过 `rbp` 可以稳定地访问局部变量（`rbp - 8` 是第一个局部变量，`rbp - 16` 是第二个，以此类推），即使 `rsp` 在函数执行过程中不断变化。

## 函数调用的完整过程

以这段 C 代码为例，一步步追踪底层发生了什么：

```c
int add(int a, int b) {
    int result = a + b;
    return result;
}

int main() {
    int x = 3;
    int y = 4;
    int z = add(x, y);
    return 0;
}
```

### 第一步：准备参数

x86-64 的调用约定（System V AMD64 ABI）规定：前 6 个整数/指针参数依次放入寄存器 `rdi`、`rsi`、`rdx`、`rcx`、`r8`、`r9`，多余的才压栈。

```
调用 add(x, y) 之前：
  edi = 3   (x 的值，放入第一个参数寄存器)
  esi = 4   (y 的值，放入第二个参数寄存器)
```

### 第二步：call 指令

`call add` 指令做两件事：
1. 把**返回地址**（call 的下一条指令的地址）压入栈
2. 跳转到 `add` 函数的入口

```
执行 call 之后：
  rsp -= 8
  [rsp] = 返回地址（main 里 call 指令的下一行）
  rip = add 的地址
```

### 第三步：函数序言（Prologue）

进入 `add` 后，编译器生成的"序言"代码建立新栈帧：

```nasm
push rbp        ; 把调用方的 rbp 保存到栈上
mov  rbp, rsp   ; 把当前 rsp 作为新帧的基址
sub  rsp, 16    ; 为局部变量 result 分配 16 字节空间（对齐到 16 字节）
```

### 第四步：函数体

```nasm
mov  eax, edi       ; eax = a（第一个参数）
add  eax, esi       ; eax = a + b
mov  [rbp - 4], eax ; result = a + b（存入局部变量）
mov  eax, [rbp - 4] ; 把 result 放入 eax（返回值寄存器）
```

### 第五步：函数尾声（Epilogue）与返回

```nasm
leave   ; 等价于：mov rsp, rbp；pop rbp（恢复调用方的 rbp）
ret     ; 从栈顶取出返回地址，跳回去
```

`ret` 执行后，`rsp` 恢复到 `call` 之前的状态，`rip` 跳回 `main`，栈上 `add` 的帧就像从未存在过一样消失了（数据还在，但 rsp 已经越过它，后续压栈会覆盖）。

## 局部变量的生命周期

栈帧这个机制，天然决定了局部变量的生命周期：

```c
void foo() {
    int a = 10;  // 分配在栈帧里
    // ... 使用 a ...
}                // 函数返回，栈帧弹出，a "消失"

int* dangerous() {
    int local = 42;
    return &local;  // 警告！返回了栈上变量的地址
}                   // 函数返回后，&local 指向的内存随时可能被覆盖
```

**返回局部变量的地址是经典的悬空指针（dangling pointer）bug**，因为函数返回后那块栈内存就"回收"了（虽然数据还在，但下次函数调用会覆盖它）。Rust 的借用检查器在编译期就能捕获这类错误：

```rust
fn dangerous() -> &i32 {
    let local = 42;
    &local // 编译错误：`local` does not live long enough
}
```

## 递归与栈深度

递归函数每次调用都会压一个新栈帧。如果递归太深，栈空间耗尽，就会发生**栈溢出（Stack Overflow）**（这也是 stackoverflow.com 名字的来源）。

```c
void infinite() {
    infinite(); // 每次调用压一个栈帧，最终 Segmentation fault
}
```

操作系统给每个线程分配的栈大小通常是固定的：Linux 默认 **8 MiB**，Windows 默认 **1 MiB**，macOS 主线程 **8 MiB**、其他线程 **512 KiB**。

假设每个栈帧 100 字节，8 MiB 的栈大约能容纳 80,000 层递归。实际上远不到这个数，因为每个栈帧的大小取决于局部变量，复杂函数的栈帧可能很大。

### 尾调用优化（TCO）

如果递归调用是函数的**最后一个操作**（尾递归），编译器可以复用当前栈帧而不是压新帧，从而让递归深度不再受栈大小限制：

```c
// 普通递归：每次调用都压新帧
int factorial(int n) {
    if (n <= 1) return 1;
    return n * factorial(n - 1); // 不是尾调用：还要做乘法
}

// 尾递归：调用是最后一个操作
int factorial_tail(int n, int acc) {
    if (n <= 1) return acc;
    return factorial_tail(n - 1, n * acc); // 尾调用
}
```

Rust 目前不保证尾调用优化（但 release 模式下 LLVM 有时会做），C/C++ 也不保证，Scheme/Haskell 等函数式语言通常保证。

## 栈的性能特点

栈的内存管理极其高效：

- **分配**：只需 `sub rsp, N`，一条指令，O(1)
- **释放**：只需 `add rsp, N` 或 `leave`，一条指令，O(1)
- **无碎片**：严格后进先出，不会产生内存碎片
- **缓存友好**：栈是连续内存，局部性好，L1 缓存命中率高

代价是：

- **大小固定**：编译期必须知道变量大小（不能有运行时才确定大小的数据）
- **容量有限**：受操作系统限制，通常几 MiB
- **不能跨函数共享**：函数返回后栈帧消失，数据无法留存

这些限制催生了**堆（Heap）**，下一篇详细讲。

## 多线程与栈

每个线程有自己独立的栈。创建新线程时，操作系统（或运行时）为它分配一块新的栈内存。这就是为什么多线程程序内存消耗会随线程数增加——每个线程至少占用一个栈的大小。

进程内存布局（从高地址到低地址）：

- **内核空间**（高地址）
- **线程 3 的栈**
- **线程 2 的栈**
- **主线程的栈**（向下增长）
- 空闲地址空间
- **堆**（向高地址方向增长）
- **BSS 段**（未初始化全局变量）
- **数据段**（已初始化全局变量）
- **代码段**（可执行指令）（低地址）

## 小结

栈是程序运行的骨架：

- 以栈帧为单位，每次函数调用压入一个栈帧，返回时弹出
- 栈帧存储：返回地址、保存的寄存器、局部变量
- rsp 指向栈顶，rbp 指向当前帧的基址
- 局部变量的生命周期与栈帧绑定，函数返回即消亡
- 分配/释放开销极低，但容量有限（几 MiB），且不能存放动态大小的数据
