## 前言

你有没有想过：两个程序都用 `0x00400000` 这个地址，为什么不会互相覆盖？4 GB 物理内存的机器上，为什么可以同时运行几十个进程，每个进程都"看到"一块完整的地址空间？程序占用的内存比物理内存还大，怎么跑得起来？

答案是**虚拟内存（Virtual Memory）**，现代操作系统最核心的机制之一。

## 为什么需要虚拟内存

设想没有虚拟内存的世界：所有进程直接共用物理内存。

```text
不良后果：

进程 A 想用地址 0x1000，进程 B 也想用 0x1000 → 冲突
进程 A 随便写 0x5000 → 可能覆盖进程 B 或操作系统内核的数据 → 崩溃/安全漏洞
程序链接时必须知道自己会被加载到哪个物理地址 → 搬动困难
```

虚拟内存解决这三个问题：**隔离**（每个进程有自己的地址空间）、**保护**（进程无法访问其他进程的物理内存）、**灵活性**（程序可以加载到任意物理地址）。

## 分页机制

### 页与页框

虚拟内存的实现基础是**分页（Paging）**：把地址空间切分成固定大小的**页（Page）**，把物理内存切分成等大的**页框（Page Frame）**，然后把虚拟页映射到物理页框。

现代系统的标准页大小是 **4 KiB**（4096 字节），也支持大页（2 MiB 或 1 GiB）以减少页表开销。

```text
虚拟地址空间（48位，只用低48位）：
┌──────┬──────┬──────┬──────┬──┐
│ 页0  │ 页1  │ 页2  │ 页3  │...│  每页 4 KiB
└──────┴──────┴──────┴──────┴──┘

物理内存（实际 RAM）：
┌──────┬──────┬──────┬──────┬──┐
│ 框0  │ 框1  │ 框2  │ 框3  │...│  每框 4 KiB
└──────┴──────┴──────┴──────┴──┘

映射关系（由页表记录）：
  进程A的虚拟页0 → 物理框5
  进程A的虚拟页1 → 物理框2
  进程B的虚拟页0 → 物理框7  ← 和进程A的虚拟页0地址相同，但物理位置不同
```

### 虚拟地址的结构

以 x86-64 的 4 级页表为例，一个 48 位虚拟地址被分成 5 个字段：

```text
虚拟地址（48 位有效位）：

 47      39 38    30 29    21 20    12 11          0
┌──────────┬─────────┬─────────┬─────────┬──────────┐
│  PML4    │   PDP   │   PD    │   PT    │  Offset  │
│  9 bits  │  9 bits │  9 bits │  9 bits │  12 bits │
└──────────┴─────────┴─────────┴─────────┴──────────┘
  L4索引     L3索引    L2索引    L1索引    页内偏移

其中：
  9 bits 可以索引 512 个条目
  12 bits 偏移 = 4096 字节 = 4 KiB（页大小）
```

### 页表遍历（Table Walk）

MMU（内存管理单元）根据虚拟地址一步步查找页表，最终得到物理地址：

```text
CPU 发出虚拟地址 → MMU 查页表 → 得到物理地址 → 访问内存

具体步骤：
1. 从 CR3 寄存器取得 PML4 表的物理地址
2. 用虚拟地址的 [47:39] 9位 索引 PML4，得到 PDP 表的物理地址
3. 用 [38:30] 9位 索引 PDP，得到 PD 表的物理地址
4. 用 [29:21] 9位 索引 PD，得到 PT 表的物理地址
5. 用 [20:12] 9位 索引 PT，得到目标页的物理基址
6. 物理基址 + 虚拟地址 [11:0] 12位偏移 = 最终物理地址
```

这个过程每次内存访问都要做 4 次额外的内存读取——听起来很慢，但 TLB 解决了这个问题（下面会讲）。

## TLB：页表的缓存

**TLB（Translation Lookaside Buffer，转译后备缓冲区）** 是 CPU 内部专门缓存虚拟→物理地址映射的硬件，访问延迟接近寄存器。

```text
CPU 访问内存时：

虚拟地址 → 先查 TLB（命中率通常 > 99%）
              ↓ 命中             ↓ 未命中（TLB miss）
           直接得到物理地址    查 4 级页表（4 次内存访问）
                                  ↓
                              填充 TLB，下次命中
```

TLB 通常只有 64~1024 个条目，容量极小，但由于**局部性原理**（程序短时间内访问的地址集中在少数页内），命中率仍然很高。

进程切换时必须**刷新 TLB**（或者用 ASID 标签区分不同进程的 TLB 条目），这也是进程切换有一定开销的原因之一。

## 页表项的标志位

每个页表项（PTE）不只存物理地址，还有一系列控制位：

```text
x86-64 页表项（64 位）：

 63      52  51       12  11  9  8  7  6  5  4  3  2  1  0
┌──────────┬─────────────┬───┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
│ 保留/NX  │  物理基址   │AVL│  │G │PS│D │A │CD│WT│US│RW│P│
└──────────┴─────────────┴───┴──┴──┴──┴──┴──┴──┴──┴──┴──┘

关键标志位：
  P  (Present)：1=页在物理内存中，0=未载入（触发缺页）
  RW (Read/Write)：0=只读，1=可读写
  US (User/Supervisor)：0=仅内核，1=用户进程可访问
  A  (Accessed)：CPU访问过此页时自动置1（OS 用于 LRU 等换页算法）
  D  (Dirty)：CPU 写过此页时自动置1（OS 用于判断是否需要写回磁盘）
  NX (No Execute)：1=此页的内容不可执行（防止数据被执行，DEP/NX 安全机制）
```

`US` 位实现了**用户空间/内核空间隔离**——内核映射的页 `US=0`，用户进程访问时 CPU 直接拒绝并产生保护错误，这就是为什么用户程序不能直接读内核内存。

## 缺页异常（Page Fault）

当 CPU 访问一个虚拟地址，但对应的页表项 `P=0`（Present 位为 0）时，MMU 产生一个**缺页异常（Page Fault）**，交给操作系统的缺页处理程序处理。

缺页不一定是错误，有三种情况：

### 1. 按需分页（Demand Paging）

程序启动时，操作系统不把所有代码/数据立刻载入物理内存，而是只建立页表映射但不实际分配物理页框（Present=0）。第一次访问时触发缺页，OS 才把对应页载入内存。

```text
时间线：

execve("./my_app")
  → OS 建立页表（P=0），不载入任何数据
  → 跳转到程序入口

访问代码页 0x401000（P=0）
  → 缺页异常
  → OS 从可执行文件读取对应的 4 KiB 数据
  → 分配物理页框，填充内容，设置 P=1
  → 返回，CPU 重新执行刚才的指令（这次 P=1，正常访问）
```

这就是为什么大型程序启动后只用了很少的内存——它只有真正用到的页才在物理内存里。

### 2. 写时复制（Copy-on-Write，COW）

`fork()` 系统调用创建子进程时，不复制所有内存，而是让父子进程共享同一批物理页框，但把两个进程的页表项都标为只读（RW=0）。第一次有进程试图写入时，触发缺页，OS 这才真正复制一个页框，让写操作只影响那一个进程。

```text
fork() 之后：

父进程虚拟页A → 物理框5（RW=0）
子进程虚拟页A → 物理框5（RW=0）← 共享同一物理框

子进程写虚拟页A：
  → RW=0，写保护缺页
  → OS 分配新框 7，复制框5的内容到框7
  → 子进程虚拟页A → 框7（RW=1）
  → 父进程虚拟页A → 框5（RW=1，恢复可写）
  → 子进程继续写，互不影响
```

COW 使 `fork()` 的开销从 O(进程内存大小) 降到 O(1)，对频繁 fork 的 Shell、Web Server 等场景非常重要。

### 3. 换页（Swapping / Paging Out）

物理内存不够时，OS 把部分页框的内容写入磁盘的 Swap 分区（或 Pagefile），然后回收这个页框给其他用途。被换出的页的 Present 位设为 0，换页信息记录在 OS 的数据结构里。

再次访问被换出的页时，触发缺页，OS 从 Swap 读回数据，放入新的物理页框，恢复 Present=1。

这就是为什么 RAM 满了程序还能跑，只是访问被换出的页会极其缓慢（磁盘 I/O 比内存慢 1000 倍以上）。

## 内存映射文件（mmap）

`mmap` 系统调用可以把文件直接映射到虚拟地址空间：

```c
#include <sys/mman.h>
#include <fcntl.h>
#include <unistd.h>

int fd = open("data.bin", O_RDONLY);
// 把文件映射到虚拟内存
void *addr = mmap(NULL, file_size, PROT_READ, MAP_PRIVATE, fd, 0);
// 现在可以用指针直接"读文件"，OS 按需缺页载入
char first_byte = ((char*)addr)[0]; // 触发缺页，读取文件第 0-4095 字节到内存
// 用完后取消映射
munmap(addr, file_size);
```

数据库、编译器、JVM 等大量使用 `mmap`——不用 `read()`/`write()` 系统调用，操作系统会自动按需把文件页载入内存和写回磁盘，简洁高效。

## 大页（Huge Page）

标准的 4 KiB 页在访问大型内存（如数据库 Buffer Pool 几十 GB）时，TLB 压力巨大——几十 GB 内存需要几千万个页表项，TLB 频繁 miss。

大页通过增大页大小（x86-64 支持 2 MiB 和 1 GiB 大页）来减少页表项数量，从而提高 TLB 命中率：

```text
访问 2 GiB 内存：
  4 KiB 页 → 524288 个页表项 → TLB 频繁 miss
  2 MiB 大页 → 1024 个页表项 → TLB 压力大幅降低
  1 GiB 大页 → 2 个页表项
```

Linux 支持透明大页（THP，Transparent Huge Pages），对程序透明地使用大页；也支持显式大页（通过 hugetlbfs 挂载点分配）。数据库（MySQL InnoDB、Oracle）、Redis、Java 堆都常配置大页以提升性能。

## 进程的内存布局

回到上一篇结尾提到的进程内存布局，现在可以理解得更深：

```text
高虚拟地址（用户空间顶部约 128 TiB）
┌──────────────────────────────────┐
│  内核空间（高 128 TiB）           │ ← US=0，用户进程无法访问
├──────────────────────────────────┤
│  栈（向下增长）                  │ ← 匿名私有映射，按需分页
│       ↓                          │
│   （未映射区域）                  │ ← 触发缺页 → Segmentation Fault
│       ↑                          │
│  mmap 区域（共享库、文件映射等） │
│       ↑                          │
│  堆（向上增长）                  │ ← brk/mmap 管理
├──────────────────────────────────┤
│  BSS 段（未初始化全局/静态变量） │ ← 全 0，COW 懒分配
├──────────────────────────────────┤
│  数据段（已初始化全局/静态变量） │ ← 从可执行文件映射
├──────────────────────────────────┤
│  代码段（只读可执行）            │ ← NX=0（可执行），RW=0（只读）
└──────────────────────────────────┘
低虚拟地址（0x400000 附近通常是代码起点）
```

代码段之所以只读（RW=0），是因为程序指令不应该在运行时被修改；如果被写入，说明有 bug 或遭到攻击，OS 直接杀进程。BSS 段的全零初始化由 OS 负责（COW 指向一个全零的物理页，第一次写入时才实际分配新页框），可执行文件里不用存 BSS 的数据。

## 小结

虚拟内存是现代操作系统最核心的抽象：

- **分页**将地址空间切分为 4 KiB 的页，建立虚拟页到物理页框的映射
- **页表**（4 级，PML4→PDP→PD→PT）存储映射关系，MMU 负责翻译
- **TLB** 缓存热点映射，使绝大多数地址翻译只需 0 额外开销
- **缺页异常**驱动按需分页、写时复制、Swap，是虚拟内存的核心机制
- **页表项标志位**实现了用户/内核隔离、只读保护、执行保护
- **大页**通过减少页表项数量缓解 TLB 压力
